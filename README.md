# SimpliiGood Creator Club — גרסה 0.3

מערכת הדגמה אינטראקטיבית לניהול קהילת יוצרים ושגרירים בישראל ובארה״ב.
נוצרה ב־5 בספטמבר 2026. גרסה 0.2 הוסיפה דחיית מועמדים, עריכה וארכוב של משימות.
גרסה 0.3 מוסיפה **מצב מחובר**: שרת ששומר את הנתונים וכניסה ליוצרים דרך קישור במייל (ראו ״הרצה עם שרת״),
ו**מסלול שגרירים**: יוצרים קטנים שעובדים בתמורה למוצרים ועמלה בלבד (ראו ״תמחור ותקציב״).

## פתיחה

פתחו את `index.html` בדפדפן במחשב. הקובץ עצמאי; אין צורך בהתקנה, בשרת או במפתח API.
אפשר גם לפתוח את הקובץ `START_WINDOWS.bat` לאחר חילוץ כל התיקייה.

הממשק מתחיל בעברית. הכפתור EN מחליף לאנגלית, ו־HE מחזיר לעברית.
אפשר לעבור בין ״מנהל התוכנית״ ל״פורטל יוצרים״ בחלק העליון.

## חשוב

כשפותחים את `index.html` כקובץ, זו **סביבת הדגמה מקומית**, לא שירות שהושק אונליין.
השורות הבאות מתארות את המצב הזה. מצב מחובר (שרת) מתואר בהמשך, ומה שעדיין חסר בו מפורט ב־`PRODUCT_SPEC.md`.

- כל הפרופילים, נתוני הקהל, המחירים, המשימות והתוכן ההתחלתי בדיוניים.
- הנתונים נשמרים בדפדפן בלבד, ככל שהדפדפן מתיר שמירה מקומית. אין סנכרון בין מכשירים.
- אין חשבונות מאובטחים, הרשאות שרת או מסד נתונים משותף.
- החלפת מצב מנהל/יוצר היא תצוגת הדגמה, לא מערכת התחברות.
- אין שליחת אימיילים, הודעות, תשלומים, פרסום ברשתות או חיבור ל־AI.
- הגשת תוכן נעשית באמצעות קישור בלבד; אין העלאת קבצים או אחסון וידאו.
- ״נתונים נבדקו״ ו״פרסום אומת״ הם סימונים ידניים בהדגמה, לא אימות באמצעות הרשתות.
- ״רישום תשלום״ אינו מעביר כסף ואינו מהווה מסמך חשבונאי.
- אין להזין פרטי יוצרים אמיתיים, פרטי בנק, סיסמאות, מפתחות API או תוכן סודי.
- המחירים והנחות השימוש בתוכן הם דוגמאות עבודה, לא מחירון מומלץ ולא הסכם משפטי.

## מסלול הבדיקה המהיר

1. בחלק העליון, עברו ל״פורטל יוצרים״. היוצרת Maya Moves / Demo נבחרת כברירת מחדל.
2. פתחו את ההצעה למשימה From freezer to smoothie, אשרו שקראתם וקבלו אותה.
3. פתחו שוב את העבודה והגישו קישור לדוגמה: `https://example.com/demo-draft`.
4. חזרו למנהל התוכנית > תוכן לאישור. פתחו את העבודה, סמנו את ארבע הבדיקות ואשרו.
5. עברו שוב ליוצרת ודווחו על פרסום באמצעות `https://example.com/demo-post`.
6. חזרו לתוכן לאישור, אמתו ידנית את הפרסום.
7. במסך התשלומים אפשר לרשום תשלום לדוגמה עם אסמכתה כגון `DEMO-001`.

קישורי example.com הם מצייני מקום. אין בהם תוכן אמיתי לבדיקה.
התהליך הזה נועד לבדיקת הממשק בלבד.

## מה אפשר לעשות

### מנהל התוכנית
- סקירה של יוצרים פעילים, תוכן לבדיקה, התחייבויות ותקציב פנוי.
- סינון בין ישראל לארה״ב; אין חיבור בין סכומי ILS ו־USD.
- צפייה בפרופילים, אישור או דחייה של מועמדים (עם סיבה), וסימון בדיקה ידנית של נתוני קהל.
- יצירת משימות עם שוק, פורמט, יעד, תקציב, מספר מקומות ומועד.
- עריכת משימה קיימת. השוק והמטבע נעולים; הפורמט נעול אחרי שיש שיבוצים; התקציב ומספר המקומות
  לא יכולים לרדת מתחת למה שכבר הוקצה.
- העברת משימה לארכיון כשאין בה עבודות פתוחות. משימה בארכיון מוסתרת מיוצרים וסגורה להצעות,
  והנתונים הכספיים שלה נשמרים. אפשר לשחזר אותה בכל עת.
- יצירת הצעות אישיות ושמירת תקציב עבורן, או הצעות שגרירים (מוצרים ועמלה) שאינן צורכות תקציב.
- אישור תוכן, בקשת תיקונים ואימות פרסום.
- רישום תשלום לדוגמה וייצוא CSV של רשומות התשלום.
- שינוי תעריפי ההדגמה להצעות חדשות בלבד.
- ייצוא וייבוא גיבוי JSON, ואיפוס הנתונים.

### פורטל יוצרים
- בחירת פרופיל דוגמה.
- צפייה בהצעות ובמשימות של הפרופיל שנבחר.
- קבלה או דחייה של הצעה.
- הגשת תוכן, צפייה במשוב והגשת גרסה מתוקנת.
- דיווח על פרסום רק אחרי אישור תוכן.
- צפייה בסטטוסים ובתגמול שהוגדר.

### הרשמה ליוצרים (מסע שאלה־תשובה)
- שאלה אחת על המסך, מעבר ב־Enter או בלחיצה, פס התקדמות, ואפשרות לחזור אחורה. בעברית ובאנגלית.
- מה שואלים: שם, אימייל, שוק, קישורים (אינסטגרם, טיקטוק, יוטיוב, פייסבוק, אתר; אחד לפחות), הבמה הראשית,
  מספר עוקבים, רמת מעורבות בבחירה (כולל ״לא בטוח/ה״), משפט על התוכן, כמה אוכל טוב נכנס לתוכן (מתורגם לציון התאמה),
  ואיך היוצר מעדיף לעבוד: תשלום, מוצרים ועמלה, או שניהם.
- לפני שליחה מוצג סיכום לאישור. הקישור הראשי נגזר מהבמה הראשית; שאר הקישורים נשמרים ומוצגים למנהל בפרטי היוצר.
- נפתח מהקישור ״הגשת מועמדות״ או ישירות עם `index.html?view=apply`. במצב מחובר זה העמוד הציבורי היחיד.
- המועמדות נשמרת מקומית ומתחילה בסטטוס ממתין לבדיקה.
- אין שליחה לחברה ואין יצירת חשבון אמיתי.

### תחומי עניין (קהלים)

לכל יוצר ולכל שיתוף פעולה יש רשימת **תחומי עניין** מתוך טקסונומיה קבועה של 35 תחומים ב־8 עולמות
(בריאות ואורח חיים, תזונה, כושר וספורט, מתכונים ושייקים, סופרפוד ומהצומח, ביצועים ואריכות ימים, משפחה,
יוצרים ופודיז). הרשימה מוגדרת פעם אחת ב־`core.js` (`INTERESTS`) והתוויות ב־`i18n.json` (`int_*`, `cluster_*`).

- בשאלון ההצטרפות היוצר בוחר עד 6 תחומים (שאלה 10 מתוך 12). מנהל יכול לשמור עד 8 לשיתוף פעולה.
- בטופס שיתוף פעולה מסמנים לאילו קהלים הוא מיועד; בכרטיסים ובפרטי היוצר מוצגים תגים.
- בהזמנת יוצר הרשימה מדורגת לפי מספר התחומים המשותפים ("3 תחומים משותפים").
- בפורטל היוצרים שיתוף פעולה עם חפיפה מסומן "מתאים לך".
- דף הנחיתה הציבורי מציג את אותם עולמות בקטע "למי זה מתאים", מאותו מקור.

## תמחור ותקציב

תחשיב ההצעה הראשוני:
עלות יצירה לפי פורמט + תעריף פרסום לפי מדרגת עוקבים × מקדם מעורבות × שיעור קהל בשוק היעד.
התוצאה של רכיב הפרסום מעוגלת ל־5 הקרובים. לבלוגים וניוזלטרים אין תמחור פרסום אוטומטי לפי עוקבים;
יש להזין את הרכיב ידנית.

המנהל יכול לערוך כל רכיב לפני יצירת ההצעה. לאחר יצירתה, המחיר נשמר ואינו משתנה עם המחירון.
שדה הבונוס הוא הצעת אחוז בלבד. ייחוס מכירות וחישוב או תשלום בונוסים **אינם ממומשים**.

### מסלול שגרירים: מוצרים ועמלה

למיקרו־אינפלואנסרים שמשווקים בלי תשלום מזומן. בהצעה בוחרים ״מוצרים ועמלה״ במקום ״תשלום ליוצר״:

- **מאגר העמלה הכולל הוא 20%** (ניתן לשינוי בהגדרות). המנהל קובע בכל הצעה כמה מזה הולך ליוצר,
  והיתרה הופכת אוטומטית להנחה לקהל. ברירת המחדל: 10% ליוצר, 10% הנחה לעוקבים.
- היוצר מקבל **חבילת מוצרים** (טקסט חופשי) ו**קוד קופון** ייחודי שהמערכת מייצרת משמו (אפשר לערוך).
- הצעה כזו **לא צורכת תקציב משימה**, אבל תופסת מקום במכסת היוצרים. משימה עם תקציב 0 היא משימת שגרירים בלבד.
- התהליך זהה: קבלה, הגשה, אישור, פרסום, אימות. בשלב **רישום התשלום** המנהל מזין את סך המכירות שיוחסו לקוד,
  והמערכת מחשבת את העמלה ליוצר. הייחוס עצמו נעשה ידנית מחוץ למערכת; אין חיבור לחנות.
- בטופס המועמדות היוצר מסמן את ההעדפה שלו, וההצעה נפתחת עם ברירת המחדל המתאימה.

תקציב משימה כולל בהדגמה תגמולי יוצרים בלבד. הוא אינו כולל מוצר, משלוח קפוא, מסים,
עמלות ספק, תוכנה או זמן ניהול. לפני פיילוט מסחרי יש להוסיף אותם לתקציב הכולל.

## דף הנחיתה הציבורי ונכסי מותג

במצב מחובר, מי שלא מחובר רואה דף נחיתה (מוצר → החבילה → למי זה מתאים → איך עובדים → מסלולים → מספרים →
שאלות). הכניסה לחברים היא מסך נפרד. במצב מקומי אפשר לצפות בו דרך "דף הנחיתה הציבורי" בסרגל הצד או
`?view=landing`.

תיקיית `assets/` מכילה נכסים אופציונליים שהדף מזהה לבד כשהם קיימים:

| קובץ | מה קורה כשהוא קיים |
| --- | --- |
| `assets/logo.png` | מחליף את סימן המילה הטיפוגרפי בכל המסכים (גרסה לבנה לרקע כהה נגזרת ב־CSS). |
| `assets/hero.jpg` | תמונת המוצר בראש דף הנחיתה, במקום האיור. |

מעלים את הקבצים לריפו (GitHub → Add file → Upload files) ו־Railway פורס מחדש. אין צורך לבנות מחדש.

## שמירת נתונים

בהגדרות אפשר לייצא גיבוי JSON. מומלץ לייצא לפני החלפת קובץ או מחיקת נתוני דפדפן.
מיקום הקובץ, דפדפן אחר, מצב פרטי או חסימת אחסון עשויים להשפיע על זמינות הנתונים.
האבטיפוס אינו מונע לחלוטין דריסת נתונים בשימוש בו־זמני; הוא מיועד להדגמה במכשיר אחד.

אם הדפדפן חוסם פתיחה מקומית או שמירה, אפשר להשתמש בשרת מקומי אופציונלי:
```bash
python serve.py
```
השרת מאזין רק ל־127.0.0.1:8765. גם במצב הזה הנתונים נשמרים בדפדפן, לא בשרת.
אין לחשוף אותו לאינטרנט.

## הרצה עם שרת (מצב מחובר, גרסה 0.3)

במקום שכל דפדפן ישמור עותק משלו, אפשר להריץ שרת אחד שמחזיק את הנתונים ומאפשר כניסה אישית:

```bash
CLUB_ADMIN_EMAILS=you@example.com node server/index.js
```

ואז פותחים http://127.0.0.1:8765/. מה משתנה במצב הזה:

- **כניסה בלי סיסמה.** מזינים אימייל ומקבלים קישור חד־פעמי (תקף 15 דקות). מנהלי התוכנית הם הכתובות
  ב־`CLUB_ADMIN_EMAILS`; יוצרים נכנסים עם האימייל שבפרופיל שלהם (מאושרים או ממתינים; מי שנדחה לא יכול להיכנס).
- **כל אחד רואה רק מה ששלו.** יוצר רואה את ההצעות והעבודות שלו ואת המשימות הפתוחות בשוק שלו, בלי פרטים של
  יוצרים אחרים, בלי תעריפים ובלי יומן פעילות. מנהל רואה הכול.
- **אותם כללים בדיוק.** השרת מריץ כל פעולה דרך `core.js`, אותה לוגיקה שהדפדפן מריץ במצב מקומי. השרת דוחה
  פעולה שלא מתאימה לתפקיד (למשל יוצר שמנסה לאשר תוכן).
- **הנתונים בקובץ.** `data/state.json` ו־`data/auth.json`. גיבוי = העתקת התיקייה. ייבוא ואיפוס מהממשק כבויים.
- **מייל.** במצב פיתוח (ברירת המחדל) אין שליחה אמיתית: הקישור מוצג במסך ונשמר ב־`data/outbox`. לשליחה אמיתית
  מגדירים `CLUB_MAIL_MODE=webhook` ו־`CLUB_MAIL_WEBHOOK_URL` שמקבל JSON עם `to`, `subject`, `text` (כל שירות
  מייל או אוטומציה שיש לו נקודת קצה כזו). כל המשתנים מתועדים ב־`.env.example`.

### פריסה ל־Railway (או Render / Fly)

1. ב־Railway: New Project → Deploy from GitHub → בוחרים את המאגר. ב־Settings → Source מוודאים שהענף הוא זה שמכיל את הקוד
   (עד המיזוג ל־`main`: `claude/migrate-gpt-project-r4zne5`).
2. Settings → Volumes → מוסיפים Volume עם Mount Path `/data`, וב־Variables מגדירים `CLUB_DATA_DIR=/data`.
   בלי זה כל פריסה מוחקת את הנתונים.
3. Variables: `CLUB_ADMIN_EMAILS=you@example.com`. `PORT`, הכתובת הציבורית וההאזנה על כל הממשקים מזוהים אוטומטית.
4. Settings → Networking → Generate Domain. הכתובת נכנסת אוטומטית לקישורי הכניסה (`RAILWAY_PUBLIC_DOMAIN`).
5. עד שיש ספק מייל, קישורי הכניסה מודפסים ללוג של השרת (מצב `console`). פותחים Deployments → View logs,
   מעתיקים את הקישור ונכנסים. כשיש ספק: `CLUB_MAIL_MODE=webhook` ו־`CLUB_MAIL_WEBHOOK_URL`.

`railway.json` ו־`package.json` שבמאגר מגדירים את פקודת ההפעלה ובדיקת התקינות (`/api/session`). אין תלויות להתקין.

**לפני חשיפה לאינטרנט:** `CLUB_SECRET` באורך 32 תווים לפחות (אחרת נוצר אוטומטית ונשמר ב־`data/secret.key`), כתובת https,
ולעולם לא `CLUB_MAIL_MODE=dev` על שרת ציבורי, כי במצב הזה קישור הכניסה מוחזר לדפדפן. עדיין אין תשלומים, העלאת קבצים, חיבור לרשתות או AI.

## קבצי המקור

- `index.html` — המערכת כקובץ עצמאי.
- `core.js` — חוקים עסקיים ומכונת מצבים; ללא DOM, נבדק ב־Node.
- `format.js` — פונקציות עיצוב טהורות (escaping, מטבע, תאריכים, CSV); ללא DOM, נבדק ב־Node.
- `app/` — הממשק, קובץ לכל מסך: `00-state.js` (מצב משותף), `10-ui.js` (רכיבים), `20-shell.js` (מעטפת וניווט),
  `30-dashboard.js`, `31-missions.js`, `32-creators.js`, `33-review.js`, `34-payments.js`,
  `35-creator-portal.js`, `36-settings.js`, `36-landing.js` (דף נחיתה), `37-login.js` (כניסה), `38-apply.js` (שאלון),
  `90-events.js` (אירועים והפעלה). הבנייה מאחדת אותם לפי סדר השם.
- `app/36-landing.js`, `app/37-login.js`, `app/38-apply.js` — העמודים הציבוריים: דף הנחיתה (המסך הראשון במצב מחובר
  למי שלא מחובר), מסך הכניסה, ומסע ההרשמה.
- `assets/` — הלוגו (`logo.png`, ראו למטה) והפונט Heebo באחסון עצמי (נטען רק כשהעמוד מוגש משרת).
- `styles.css` — עיצוב מותאם למסך מחשב ומובייל, עברית ואנגלית.
- `i18n.json` — טקסטי הממשק.
- `build.py` — בנייה מחדש של index.html, ללא תלויות נוספות. `--check` מוודא שהקובץ מעודכן.
- `serve.py` — שרת סטטי מקומי למצב ההדגמה (127.0.0.1 בלבד).
- `server/` — השרת של המצב המחובר: `index.js` (HTTP ו־API), `auth.js` (קישורי כניסה ועוגיות חתומות), `store.js` (אחסון JSON, נקודת ההחלפה למסד נתונים), `config.js` (משתני סביבה).
- `.env.example` — כל משתני הסביבה של השרת עם הסבר.
- `START_WINDOWS.bat` — פתיחת index.html בווינדוס.
- `test_core.js` — בדיקות כללי המערכת.
- `test_format.js` — בדיקות יחידה לפונקציות העיצוב.
- `test_ui.py` — בדיקות דפדפן למצב ההדגמה; Playwright דרוש לבדיקות בלבד.
- `test_server.js` — בדיקות API לשרת: כניסה, הרשאות, סינון נתונים, הקשחה.
- `test_ui_server.py` — בדיקות דפדפן למצב המחובר, כולל זרימת הכניסה המלאה.
- `PRODUCT_SPEC.md` — היקף הגרסה והעבודה הנדרשת לשירות אמיתי.
- `TEST_RESULTS.md` — מה נבדק ומה טרם אומת.

### הלוגו

שימו את קובץ הלוגו הרשמי בנתיב `assets/logo.png` (רקע שקוף, רוחב 1200 פיקסלים לפחות). מרגע שהקובץ קיים,
כל המסכים (דף הנחיתה, הכניסה, ההרשמה, סרגל הניהול) מציגים אותו; הגרסה הלבנה לרקעים כהים נגזרת אוטומטית.
`python build.py` גם מטמיע אותו בתוך `index.html`, כך שהקובץ העצמאי נושא את המותג. עד אז מוצג סימן טיפוגרפי
בסגנון הלוגו (SIMPLiiGOOD / SPIRULINA).

## בנייה ובדיקות למפתח

```bash
python build.py
node test_core.js
node test_format.js
node test_server.js
python test_ui.py
python test_ui_server.py
```

עורכים קבצים ב־`core.js`, `format.js`, `app/`, `styles.css` או `i18n.json`, ואז מריצים `python build.py`.
אין לערוך את `index.html` ידנית.

בדיקות הדפדפן מרימות שרת מקומי זמני על 127.0.0.1 ורצות ב־Chromium אמיתי עם אחסון דפדפן אמיתי,
לאורך כל מסלול הבדיקה המהיר שלמעלה. Playwright נדרש לבדיקות בלבד:
```bash
pip install playwright && python -m playwright install chromium
```
כל הפקודות רצות אוטומטית ב־GitHub Actions בכל דחיפה (`.github/workflows/ci.yml`).
ה־CI נכשל אם `index.html` לא נבנה מחדש אחרי שינוי בקבצי המקור.
עדיין מומלץ לבצע בדיקת קבלה במחשב המשתמש, במיוחד פתיחה מקובץ בווינדוס.
